# ADR-0004：新旧数据库并存遵守单写者与整体切换

- 状态：已接受
- 日期：2026-07-16
- 决策阶段：阶段 1（架构决策与契约固化）
- 适用范围：并行验证、Schema 管理、数据迁移、生产切换与回滚

## 上下文

阶段 0 确认旧 PostgreSQL `public` schema 有 70 张物理表、617 个物理列，旧 Alembic 为单一 head `f5b6c7d8e9f0`；`03-data-ownership.csv` 还记录了 84 类数据库 KV、Redis、队列、任务、文件与第三方资源。旧 Flask 与新 Java 需要长期并行开发，但若它们写同一数据库，就无法区分行为差异、回滚写入或证明每类事实的唯一所有者。

最终目标是以整个新部署替换旧部署，而不是让网关把部分路由切到 Java、其余路由继续由 Flask 写同一组表。阶段 0 运行手册已经定义四套隔离验证环境和“停止旧写入后才能迁移”的状态机。

## 决策

### 并行验证

并行验证固定使用四个隔离环境：

| 环境 | 运行时 | 数据库权限 | 用途 |
| --- | --- | --- | --- |
| `legacy-read` | Flask | 只读 | 旧只读响应基准 |
| `java-read` | Java | 只读 | Java 只读响应对比 |
| `legacy-write` | Flask | 只写本库 | 在基础快照 A 上执行旧命令 |
| `java-write` | Java | 只写本库 | 在同源基础快照 B 上执行新命令 |

四套环境必须使用不同数据库、角色、端口、Redis、队列、对象卷和外部 stub。写请求对比是“同一命令分别作用于两个同源快照，然后比较终态”，绝不是一次请求同时写两边。

### Schema 与所有权

1. 并行期旧数据库只由旧 Alembic 推进，新 Java 的目标数据库只由 Ti-Java 的迁移链推进；二者不共同管理同一实例。
2. 阶段 2～7 对旧结构副本只做读取映射与 `ddl-auto=validate`。Hibernate 在任何非一次性测试环境都不得 `create`、`update` 或 `create-drop`。
3. 正式 Flyway baseline 只在阶段 8 创建，且必须记录与旧 head `f5b6c7d8e9f0`、结构摘要和备份校验和的对应关系。此前的测试建表 SQL 只是隔离夹具，不能伪称生产 baseline。
4. baseline 之后的变更由 Flyway 唯一管理，优先 additive change。删除列、改类型或重命名必须等旧读写方退出且恢复/反向迁移演练完成。
5. 应用数据库角色无 DDL 权限；迁移使用单独、短时授权的角色。PostgreSQL 是业务事实源，Redis 内容必须可重建。
6. `03-data-ownership.csv` 中每个资源必须映射到唯一目标模块。跨模块外键可以保留数据库完整性，但 Java 对象只保存对方 ID，所有者之外的模块无写表权限。

### 最终切换与回滚

生产切换只能在另行授权的维护窗口按 `Prepared → Frozen → BackedUp → Migrated → Validated → Switched → AcceptingWrites` 推进：先拒绝写流量、停 Worker/定时任务、撤销旧写权限并用连接审计证明写入者为零，随后备份、恢复到新库、执行受审 Flyway、校验并整体切换入口。

Java 开始接收业务写入前，可停止 Java 并整体回到未变化的旧源库。Java 已接收写入后，禁止直接指回冻结快照；必须重新冻结，优先前向修复，或将 Java 写入纪元通过受审反向迁移导入第三套回滚库，再完整校验。

## 后果

正面后果：

- 任何写入都能归属到一个运行时，差异报告和回滚证据可信。
- 旧源数据库在切换期间保持可恢复、只读和可审计。
- Schema 演进不会由 Hibernate 启动副作用或两套迁移工具竞态触发。

代价与风险：

- 并行写比较需要四套数据设施和可重复恢复，资源消耗高于共享一个开发库。
- 最终切换需要维护窗口，不能用双写“消除”停机时间。
- Java 开放写入后的回滚不是简单切流，必须处理新写入纪元。

## 拒绝的方案

- **Flask 与 Java 同写一库：** 无法证明唯一所有者，失败时无法安全撤销一方写入。
- **按路由渐进代理到两个后端：** 多个领域共享表与事务，会形成隐式双写和跨运行时不变量破坏。
- **应用启动时由 Hibernate 更新 Schema：** 不可审查、不可预测，无法与备份和迁移版本绑定。
- **Java 直接接管正在服务的旧库：** 缺少不可变恢复点，也无法让旧库保持回滚基准。
- **用 Redis 快照代替业务备份：** 阶段 0 已确认 Redis 采用 `allkeys-lru` 且只允许保存可重建状态。
- **Java 写入后直接回旧冻结库：** 会静默丢失窗口内用户数据。

## 实施与验证约束

每次对比/切换演练必须机器记录：提交、镜像 digest、快照 SHA-256、Alembic/Flyway 版本、数据库 DSN 的脱敏标识、角色权限、连接审计、表摘要、对象清单和时间边界。

自动化门禁至少断言：

- 四个环境的数据库/Redis/卷标识互不相同，旧/新进程无法解析对方写入 DSN；
- read 角色执行 INSERT/UPDATE/DELETE/DDL 均失败；application 角色执行 DDL 失败；
- Java 所有 Profile 的 Hibernate 配置为 `validate` 或更严格；
- 70 张物理表与所有新增 Flyway 表通过结构、约束、索引、序列和所有者对账；
- 同源双快照的写测试比较行级规范化结果、聚合、事件、文件哈希和失败回滚，而不只比较 HTTP 200/行数；
- 任一环境连接到对方数据库、发现双写或未授权 Schema 漂移时立即失败；
- 生产 Compose 不包含父目录挂载、Flask upstream、影子写请求或旧数据库写凭据。
